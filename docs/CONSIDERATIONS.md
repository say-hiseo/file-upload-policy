## 0. 기획 (Scope & Approach)

### 0-1. 블랙리스트 vs 화이트리스트

**판단**: 요구사항 원안대로 블랙리스트(차단 목록 관리) 방식 유지

> **근거**
> - 화이트리스트가 "목록에 없는 신종 위험 확장자까지 기본 차단"되어 보안적으로
>   더 안전하다는 걸 인지하고 있으나, 과제 요구사항이 "확장자 차단 정책 관리"로
>   명시되어 있어 이를 벗어나지 않음

⇒ **한계**: 블랙리스트는 "아직 등록되지 않은 위험 확장자"를 구조적으로 막지 못함. 실서비스 전환 시 화이트리스트 방식을 권장

### 0-2. 업로드 파일의 처리 범위 — 저장까지만

**판단**: 업로드된 파일을 서버가 실행하거나 해석(압축 해제, 스크립트 실행, 이미지
리사이징 등)하는 기능은 만들지 않음

> **근거**
> - 실행/해석 기능이 없으면 ZIP Slip, RCE 등 다수의 2차 공격 벡터가 애초에
>   성립하지 않음. 범위를 "안전한 저장소"로 명확히 좁힘

### 0-3. 정책 판단 로직의 단일 소스화

**판단**: 정책 관리 화면(A)과 실제 업로드 검증(B)이 동일한 조회 기준
(`ExtensionPolicyRepository.findByBlockedTrue()`)을 공유

> **근거**
> - 화면과 검증 로직이 분리된 채 각자 구현되면, 화면상 체크했는데 실제로는 안
>   막히는(혹은 반대) 정합성 문제가 생길 위험이 있음

### 0-4. 정책은 전역(Global) 상태다

**판단**: 확장자 차단 정책(고정/커스텀 모두)은 로그인 계정과 무관하게 시스템
전체에 단 하나만 존재. test1이 exe를 차단하면 test2도, 게스트도 동일하게 봄

> **근거**
> - 요구사항 원문이 서비스 전체에 적용되는 단일 정책을 전제로 함
> - `extension_policy`에 소유자 컬럼이 없고, `extension`에 전역 UNIQUE 제약으로
>   "이 확장자에 대한 정책은 시스템에 단 하나"임을 스키마 레벨에서 강제
> - 방화벽/보안 콘솔처럼 여러 관리자가 공유하는 설정이라는 성격에 부합
> - 로그인은 정책 내용이 아니라 감사 로그의 "누가 바꿨는지"에만 영향을 줌.
>   업로드 이력(2-5)은 반대로 사용자별 분리 대상이라, "정책=전역" vs
>   "이력=개인별"로 기준이 다름을 구분해야 함

```
확장 고려
조직/사용자별 정책이 필요해지면 owner_id 컬럼 추가로 확장 가능하도록,
정책 조회 로직을 처음부터 "조건에 대한 조회" 형태로 작성해둠
```

## 1. 검증/보안 관점

### 1-1. 확장자만으로 판단해도 되는가 — 매직바이트 검증

**판단**: 채택(부분) — Windows PE(`MZ`), 스크립트 셔뱅(`#!`) 등 대표적인 실행
파일 시그니처를 확장자 검사와 함께 적용

> **근거**
> - `report.jpg`로 위장한 exe 실행 파일이 이 과제가 막으려는 핵심 위협.
>   확장자 정책은 1차 방어선, 매직바이트 검증은 2차 방어선
> - 실증: 확장자는 jpg(차단 목록 밖)지만 내용은 MZ 헤더인 테스트 파일로 검증
>   완료 — 확장자 검사를 통과해도 매직바이트 검사에서 정상 거부됨을 DB
>   기록으로 확인

⇒ **한계**: 모든 포맷의 시그니처 종합 판별(Apache Tika 수준)은 시간상 제외, 위협도가 높은 실행 파일류만 우선 적용

### 1-2. 대소문자 / 이중 확장자

**판단**: 채택 — 파일명을 `.` 기준으로 전부 분리해 모든 조각을 정규화 후 차단
목록과 대조 (`FileNameParser`)

```
file.exe.txt   → 분리: [exe, txt] → 'exe'가 차단목록에 있으면 거부
archive.tar.gz → 분리: [tar, gz]  → 둘 다 없으면 통과
```

> **근거**
> - "점 개수 2개 이상이면 거부"는 `tar.gz` 같은 정상 파일을 오탐하고,
>   "마지막 확장자만 검사"는 `file.exe.txt` 우회를 놓침. 모든 조각을 개별
>   검사해 두 문제를 동시에 해결

### 1-3. 확장자 없는 파일 / 숨김 파일 / 긴 파일명

**판단**
- 확장자 없는 파일 → 통과 (차단 안 함)
- `.env`, `.gitignore` 등 → "확장자 없음"으로 별도 취급
- 255자 초과 파일명 → 업로드 단계에서 사전 거부 (`FILENAME_TOO_LONG`)

> **근거**
> - `Dockerfile`, `Makefile` 등 확장자 없이 쓰이는 정상 사례가 존재해, 확장자
>   없음을 이유로 차단하는 건 과함
> - 긴 파일명은 OS/DB 컬럼 길이 제약으로 인한 저장 실패를 사전 차단하기 위함

### 1-4. 확장자 입력값 정규화 규칙

**판단**: 채택 — 아래 파이프라인(`ExtensionNormalizer`)을 정책 등록(A)과 업로드
검증(B) 양쪽에 동일 적용

```
1. null byte 제거/거부
2. 앞뒤 공백 제거 (strip)
3. NFKC 정규화
4. 유니코드 제어/포맷 문자 거부 (RTLO U+202E 등)
5. 소문자 변환
6. 앞뒤 '.' 제거
7. 허용 문자 화이트리스트 검증: ^[a-z0-9]+$
8. 정규화 후 빈 문자열이면 거부
```

> **근거**
> - 각 단계가 대소문자 우회, 유니코드 위장(RTLO), 유사 문자 우회를 순서대로 차단
> - 단위테스트 32건으로 검증 (대소문자, 점 처리, 공백, 특수문자, null byte,
>   RTLO, 전각문자, null/빈값 등)

### 1-5. 서버 사이드 검증의 필요성

**판단**: 채택 (원칙으로 명문화)

> **근거**
> - 클라이언트 검증은 UX 개선용일 뿐 우회 가능. 최종 판단은 반드시 서버에서

### 1-6. 업로드 파일 크기/개수 제한

**판단**
- 파일당 크기: 최대 10MB (앱 레벨) + nginx `client_max_body_size` 100M (이중 방어)
- 요청당 개수: 최대 10개, 각 파일 독립 검증

```json
{ "results": [
    {"filename": "report.pdf", "status": "SUCCESS"},
    {"filename": "virus.exe",  "status": "REJECTED", "reason": "..."}
]}
```

> **근거**
> - 크기 제한 없으면 대용량 파일로 디스크/메모리 고갈 가능. 앱 레벨만 걸면
>   요청이 이미 애플리케이션까지 도달한 뒤 걸러져 리소스 낭비 → nginx에서 먼저 차단
> - 개수는 파일별 독립 검증이 가능해야 "부분 성공" 응답이 의미가 있음

### 1-7. 저장 시 원본 파일명 사용 위험

**판단**: 저장 파일명은 UUID v4로 재생성, 원본 파일명은 DB에 표시/다운로드용으로만 보관

```
원본 그대로        → Path Traversal, 덮어쓰기 위험 → 탈락
Auto Increment ID → 예측 가능(enumeration 위험)   → 탈락
파일 해시(SHA-256) → dedup 이점 있으나 목적과 무관한 최적화 → 제외
UUID v4           → 추측 불가능, 즉시 생성 가능    → 채택
```

> **근거**
> - `GET /api/uploads/{id}/download`에서 소유권 검증(본인 파일만 401/403
>   구분), 정적 서빙 경로 밖 저장, `Content-Disposition: attachment` 강제로
>   접근 통제를 완성함
> - `stored_filename`에 unique 제약을 걸어 충돌 시 조용히 덮어쓰지 않고
>   명시적으로 실패하도록 함

### 1-8. MIME 스푸핑 및 우회 패턴 종합 검토

**판단**
- MIME 헤더: 신뢰하지 않음. 매직바이트와 다르면 로그에만 기록(교차검증 신호)
- `.php.jpg` 등 이중 확장자: 1-2의 "모든 조각 검사"로 대응
- SVG 내부 스크립트: 업로드/다운로드 응답 모두 `application/octet-stream` +
  `attachment` 강제로 렌더링 자체 차단
- 임시 파일 잔여 방지: 확장자 → 매직바이트 → (통과 시에만) 저장 순으로 설계
- 로그 인젝션 방지: 파일명의 개행 문자를 로그 기록 전 제거/이스케이프
- Content-Disposition 헤더 인젝션 방지: 다운로드 API의 파일명을 헤더에 넣기
  전 개행/제어문자/따옴표 제거, RFC 5987 형식으로 인코딩
- Linux 환경 확장자 없는 실행 파일: shebang(`#!`) 시그니처를 매직바이트 검증에 포함

> **근거**
> - SVG는 정상 이미지 포맷이면서 XML이라 `<script>`를 담을 수 있어 확장자/
>   매직바이트 차단으로는 원천 차단 불가능
> - "확장자 없음 = 안전"은 Windows 파일 연결 관례 기반 가정이라, Linux
>   서버에서는 유효하지 않을 수 있음

⇒ **한계**: ZIP Slip은 압축 해제 기능 자체가 없어 해당 없음(0-2 참고). EXIF 등 메타데이터 stripping과 SVG 내부 `<script>` sanitize(DOMPurify 등)는 별도 라이브러리가 필요해 우선순위상 제외, 실무 전환 시 필요

### 1-9. Fail-Closed 원칙

**판단**: 정책 DB 조회 자체가 실패하면 업로드를 거부(fail-closed). 조회 실패 시
통과(fail-open)로 만들지 않음

> **근거**
> - fail-open이면 DB 장애가 곧 보안 정책 전체의 무력화로 이어짐. 보안 정책
>   설계에서 놓치기 쉬운 지점

## 2. 정책/데이터 관점

### 2-1. 고정/커스텀 확장자가 겹칠 때

**판단**: `extension` 컬럼 전역 unique 제약으로 구조적 방지. 커스텀에 `exe`
입력 시, 등록 전 조회에서 이미 `type='FIXED'`인 row 발견 → INSERT 시도 없이
`FIXED_EXTENSION_CONFLICT`로 거부

> **근거**
> - `(extension, type)` 복합 unique였다면 exe가 FIXED/CUSTOM에 동시 존재
>   가능해짐. 단일 컬럼 전역 unique로 이를 원천 차단

### 2-2. 정책 변경 이력/감사

**판단**: 채택 — 정책 테이블(현재 상태)과 별도로 이력 테이블
(`extension_policy_audit_log`, INSERT-only)을 두어 시간순 기록. 조회 API는
`GET /api/policies/audit-logs`

> **근거**
> - "누가"는 정식 인증이 범위 밖이라 판단해 더미 세션 로그인 + `member`
>   테이블로 식별. 로그인 시 실제 계정명, 비로그인 시 `SYSTEM`으로 기록
>   (요청 자체는 막지 않음)
> - 이 테이블엔 성공한 변경만 기록됨(거부 시도는 트랜잭션 롤백으로 애초에 안
>   남고, 애플리케이션 로그에만 남음 — 4-2 참고). 그래서 API 응답에 별도
>   "결과" 필드를 두지 않고 프론트가 고정 텍스트로 "성공"만 표시

### 2-3. 200개 / 20자 제한과 동시성

**판단**
- 20자: `VARCHAR(20)` + Bean Validation `@Size` 이중 검증
- 200개: 애플리케이션 레벨에서 카운트 후 판단
- 200/200 도달 시 입력창/버튼 사전 비활성화
- 동시성(TOCTOU) 방어: `PESSIMISTIC_WRITE` 락(`findByTypeForUpdate`,
  `SELECT ... FOR UPDATE`)으로 최종 방어

> **근거**
> - 200개는 DB 제약이 아닌 애플리케이션 레벨 판단이 정책 변경(예: 500개로
>   상향)에 더 유연함
> - 두 요청이 동시에 199→200번째로 추가 시도하면 "개수 확인"과 "INSERT"
>   사이 시간차로 제한이 뚫릴 수 있음을 확인해 락으로 방어
> - 낙관적 락 대신 비관적 락을 택한 이유: 한도 근처에서 몰리는 동시 요청은
>   낙관적 락(재시도 유도)으로는 계속 충돌해 사용자 경험이 나빠짐

### 2-4. 대량 조회 시 성능

**판단**: 인덱스는 적용, 캐싱 등 추가 최적화는 이번 규모에서 제외

> **근거**
> - 현재 규모(최대 207개)에서 인덱스 유무가 체감 성능에 영향 없음

```
확장 고려
트래픽 증가 시 정책 변경 시에만 무효화하는 애플리케이션 캐시 도입.
Redis는 이번 규모에 과함
```

### 2-5. 업로드 이력의 접근 범위 — 본인 것만 vs 전체 공유

**판단**: 로그인 사용자 "본인이 올린 파일만" 조회 가능. 비로그인은 401로 거부

```
실무 패턴 비교
A) 완전 개인화 — 본인 것만 (Google Drive형)
B) 조직 공유   — 로그인만 하면 전체 열람 (Notion, Jira 첨부파일형)
C) 완전 공개   — 로그인 없이도 열람 (GitHub public 커밋 이력형)
```

> **근거**
> - 이 프로젝트 성격(보안 관제 콘솔)상 패턴 B가 실무에 더 가까울 수 있다고
>   판단했으나, 패턴 A가 이미 구현되어 있고 보안적으로 더 보수적인 선택이라 유지
> - 여러 게스트의 기록이 `SYSTEM` 이름으로 뒤섞여 노출되면 사실상 익명 전체의
>   업로드 목록이 되어 프라이버시 문제가 생김. "본인 확인이 안 되면 '본인 것'
>   이라는 개념이 성립하지 않는다"는 원칙
> - "게스트도 이용 가능" 원칙은 핵심 기능(A, B)이 로그인 여부로 막히지
>   않는다는 뜻이지, 모든 부가 기능이 동일해야 한다는 뜻은 아님. 업로드
>   자체는 게스트도 가능하고, 이력 재조회만 로그인을 요구

```
확장 고려
Repository의 memberId 필터 조건 하나만 제거하면 패턴 B(조직 공유)로
즉시 전환 가능하도록 설계해둠
```

## 3. UX/예외 관점

### 3-1. 차단 시 메시지

**판단**: "무엇이" + "왜"를 분리해 명확히 전달
- 예: `report.exe 업로드가 거부되었습니다 — 사유: 'exe' 확장자는 차단되었습니다`

> **근거**
> - 백엔드 `ErrorCode` enum이 완결된 문장을 조립해 내려주므로 프론트는
>   그대로 노출하면 됨

### 3-2. "선택된 파일"과 "업로드 결과"의 상태 분리

**판단**: 아직 서버에 안 보낸 "선택된 파일"과, 서버가 응답한 "업로드 결과"를
별개의 로컬 상태로 분리. "업로드 결과"는 `POST /api/uploads` 응답을 로컬
상태에 저장해 렌더링(로그인 여부 무관, 항상 표시). "내 업로드 이력"(로그인
전용)은 완전히 별개 기능으로 유지

> **근거**
> - 초기엔 업로드 완료 파일을 목록에서 제거하고 로그인 전용 이력 API에서만
>   보여주도록 했는데, 이러면 비로그인 사용자가 방금 자신이 올린 파일의 거부
>   사유를 볼 수 없어 요구사항 B("로그인 여부와 무관하게 명확한 사유 전달")를 위반함
> - 재업로드 방지는 파일별 상태 플래그로 처리 — 처리 완료된 파일은 재전송
>   대상에서 제외, 결과는 화면에 계속 남음
> - 실패 유형별 재시도 UX 차등: 정책 위반 거부(재시도해도 동일 결과)는
>   재시도 버튼 없이 목록에서 제거, 네트워크/5xx 오류(재시도 시 성공
>   가능)는 목록에 남겨 재시도 허용

### 3-3. 로딩/에러/네트워크 실패 상태

**판단**
- 낙관적 업데이트 사용 시 실패하면 반드시 원상복구
- 서버 에러와 네트워크 에러를 구분해 다른 메시지로 안내
- 진행 중에는 관련 버튼 비활성화
- 업로드 진행률(%)은 구현하지 않음

> **근거**
> - 백엔드가 청크 스트리밍을 안 해 정확한 진행률 표현이 불가능. "업로드
>   중..." 스피너로 단순화 (가짜 진행률 애니메이션은 정직하지 않다고 판단)

### 3-4. 저장 실패 시 화면-DB 정합성

**판단**: 서버 응답 전까지 화면 상태를 최종 확정하지 않음 (체크박스, 커스텀
목록, 카운트 모두 동일 원칙)

### 3-5. 접근성/반응형

**판단**
- 접근성: label 연결, aria-label(삭제 버튼 등), `aria-live="polite"` 알림,
  키보드 조작(Tab/Space/Enter), 색상 외 정보 병행 제공
- 반응형: 데스크톱 우선, 768px 이하에서 최소한의 1열 스택만 적용

⇒ **한계**: 모바일 터치 최적화는 관리자 화면 특성상 우선순위 낮다고 판단해 제외

### 3-6. 삭제 확인 절차

**판단**: 커스텀 확장자 X 클릭 시 확인 모달 없이 즉시 삭제

> **근거**
> - 요구사항 원문에 확인 절차 언급이 없고, 실패 시 롤백(3-4)이 이미 있어
>   낙관적 삭제로 충분히 안전

### 3-7. 데모용 로그인 안내 UI

**판단**: 로그인 화면에 더미 계정(test1/1234, test2/5678)을 노출

> **근거**
> - 실서비스라면 안 되는 UX이지만, 심사자가 바로 로그인 검증해야 하므로
>   의도적으로 노출

⇒ **한계**: "실서비스라면 제거해야 할 데모 전용 UI"임을 명시

## 4. 운영 관점

### 4-1. 새로고침/동시 편집 정합성

**판단**: 실시간 동기화(웹소켓)는 제외, 새로고침 시 재조회로 충분

> **근거**
> - 200개 제한의 Race Condition은 2-3에서 DB 레벨(비관적 락)로 최종 방어하므로,
>   화면 갱신 자체는 재조회만으로 충분

### 4-2. 로그/모니터링

**판단**
- 정책 변경 이력, 업로드 결과 이력 — DB 테이블 + 조회 API 구현 완료
- 애플리케이션 로그(stdout → Docker 컨테이너 로그) — 거부 사유, 요청 정보,
  매직바이트 불일치 등 (파일명은 로그 인젝션 방지 처리된 값만 기록)

⇒ **한계**: 별도 모니터링 대시보드/알림은 범위 제외 — 현재 규모는 DB 직접 쿼리로 대체 가능

```
확장 고려
트래픽 증가 시 중앙 로그 시스템(ELK 등) 필요
```

### 4-3. Docker 볼륨과 재배포 안전성

**판단**: 업로드 파일 디렉토리와 DB 데이터를 각각 Docker Volume으로 호스트에 마운트

> **근거**
> - 컨테이너는 stateless가 기본 전제라, 마운트 없이는 재시작/재배포 시
>   데이터가 전부 유실됨

### 4-4. 컨테이너 재시작 정책

**판단**: 모든 서비스에 `restart: unless-stopped` 적용

> **근거**
> - 서버 예기치 않은 재부팅/장애 시 자동 복구
> - `always`가 아닌 `unless-stopped`를 택한 이유는, 관리자가 명시적으로
>   멈춘 경우(점검 등)까지 자동 재시작되면 오히려 방해가 되기 때문

### 4-5. 배포 인프라의 접근 제어 (NCP ACG)

**판단**: 최소 권한 원칙 적용
- 불필요한 RDP(3389) 포트 제거
- 80(HTTP)은 심사 목적상 전체 개방 불가피
- 22(SSH)는 전체 개방 상태로 둠

> **근거**
> - Linux 서버에 Windows 원격 데스크톱(RDP)은 불필요 — 안 쓰는 포트를
>   열어두는 것 자체가 불필요한 공격 표면

⇒ **한계**: 22(SSH)는 이상적으로는 특정 IP로 제한해야 하나, 접속 환경이 유동적이라 전체 개방 상태로 둠. 실서비스라면 IP 제한 또는 VPN 경유가 필요

### 4-6. DB 자격증명 하드코딩

**판단**: `docker-compose.yml`에 DB 계정/비밀번호를 평문 환경변수로 기술

> **근거**
> - 과제 규모와 시간 제약상 별도 시크릿 관리 도구를 도입하지 않음. 심사
>   편의성(누구나 즉시 재현 가능해야 함)과 운영 보안 사이의 트레이드오프로
>   편의성을 우선함

⇒ **한계**: 실서비스라면 `.env`(git 제외) 또는 시크릿 관리 서비스로 분리해야 함. public 저장소에 이 상태로 올라가 있는 것 자체가 실무 기준에는 안 맞는다는 걸 인지하고 있음

### 4-7. 향후 확장 시나리오

| 항목 | 현재 | 확장 조건 |
|---|---|---|
| 저장 방식 | 로컬 파일시스템 + Docker Volume | 스케일 아웃 시 Object Storage 전환. `stored_filename`이 이미 "식별자" 역할만 해 스키마 변경 불필요 |
| 인증/인가 | 더미 로그인 + 세션 | 실사용자 증가 시 Spring Security + 해싱 + Role 기반 인가 |
| 정책 관리 범위 | 전역 단일 정책 | `owner_id` 컬럼 추가로 조직/사용자별 분리 가능하도록 조회 로직 설계해둠 |
| 차단 방식 | 블랙리스트 (`FIXED`/`CUSTOM`) | 화이트리스트 전환 시 값 체계만 `ALLOWED`/`BLOCKED`로 변경, 재설계 불필요 |
| 조회 성능 | 인덱스만 | QPS 병목 시 애플리케이션 캐시 도입 |
| 업로드 이력 범위 | 본인 것만 (패턴 A) | Repository 필터 제거만으로 패턴 B(조직 공유) 전환 가능 |
