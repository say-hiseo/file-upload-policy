이 프로젝트는 세 갈래(기획/백엔드, 프론트엔드 설계-코드화, 프론트-백엔드 연동)로 나뉘어 진행됐고, 각각 다른 AI 도구/세션을 거쳤습니다. 4-1은 시간순 프롬프트 기록, 4-2는 사용한 도구/스킬, 4-3은 결과물을 어떻게 취사선택했는지 회고입니다.

# 4-1. 프롬프트/입력 기록 (시간순)

<details>
<summary><h2>기획 및 설계 (Claude)</h2></summary>
<div markdown="1">

### ① 과제 설명 붙여넣기 → 기술 스택 질문

과제 원문을 그대로 붙여넣고 "백엔드는 자바, 프론트는 리액트로 사용하는 게 베스트일까요? DB는 PostgreSQL/MySQL/Redis 중 뭐가 나을까요?"로 시작. 정답을 찾기보다 "이 과제 목적(고려사항 깊이, AI 활용)에 시간을 더 쓰는 게 유리한 스택이 뭔지"를 먼저 물어봄.

### ② 실제 경험/채용공고 정보를 추가로 제공 → 스택 재조정

"Java/Spring, Docker, NCP 경험 있고, 채용 공고에 Spring/AWS/Docker/Linux가 명시돼 있다"고 알려줌 
→ AI가 처음 추천했던 Node.js/Next.js 대신 Spring Boot + React로 스택을 다시 정함. 이후 배포 인프라(AWS vs NCP)를 놓고 "실배포 시 AWS는 과금되지 않냐"고 반문 
→ 크레딧이 남은 NCP로 최종 결정 (4-3 "폐기한 것" 참고).

### ③ 요구사항 정의서 작성 요청, 형식을 두 번 반려

처음 나온 요구사항 정의서에 스키마/쿼리(SQL)까지 섞여 있는 걸 보고 "이거 실무에서도 이런 식으로 작성하나요? 스키마를 아직 안 짰는데 과한 거 아닌가요?" 라고 반문 
→ 동작(behavior)·제약(constraint)만 남기고 구현 세부사항은 제거하도록 재작성 지시.

### ④ 스키마 설계 — 4단계에 걸쳐 반박하며 다듬음

- **1차**: 고정 확장자를 seed row로 둘지, 체크된 것만 존재하게 할지 두 안을 비교시킴 → 예시로 설명해달라고 재요청해 정확히 이해 후 seed 방식 확정
- **2차**: "고정 확장자는 커스텀 영역에 표시 안 됨"이 정확히 뭘 의미하는지 캐물어, 전역 unique 제약 하나로 해결되는 구조를 확인
- **3차**: `created_at`/`updated_at`을 모든 테이블에 관성적으로 넣은 것에 "삭제 대신 update로 비활성화하는 게 안전하다고 알고 있었다"며 원칙 자체를 재검토 요구 → "상태 엔티티/불변 로그"로 나누는 기준 정립
- **4차**: FK 관계가 아예 없는 걸 보고 "테이블끼리 연관관계나 외래키는 없냐"고 지적 → FK+스냅샷 컬럼 병행 구조로 보완

### ⑤ 기획/보안/예외/운영 고려사항(CONSIDERATIONS.md) 초안 요청, 반복 재작성

초안이 "채택/제외" 딱지만 붙은 수준이라 "이 정도로 충분하냐"고 반박 
→ 근거·대안 비교까지 담긴 버전으로 재작성. 특히 이중 확장자 처리, 정규화 규칙, 업로드 개수 제한 등에서 직접 반례를 들어 규칙을 다시 짜게 함 (4-3 "수정해서 채택한 것" 참고).

 <h2>백엔드 구현 (Claude)</h2></summary>

### ⑥ 프로젝트 초기화

처음엔 Kotlin DSL로 스캐폴딩을 받았으나 "Groovy로 프로젝트를 설계하고 싶다"는 요청으로 Spring Initializr(Boot 4.1.1) 기반으로 다시 시작. Boot 4의 모듈화된 스타터 이름이 알던 것과 달라 웹 검색으로 실제 변경 사항을 확인한 뒤 안내받음 (4-3 "폐기한 것" 참고).

### ⑦ 로컬 개발 환경 트러블슈팅 (반복)

PowerShell `Out-File`이 BOM을 붙여 Java 컴파일 실패가 여러 파일에서 반복 발생 
→ `.NET UTF8Encoding($false)` 방식으로 해결.
이 외에도 관리자 권한 PowerShell의 상대경로 문제(`$PWD`와 .NET 현재 디렉토리 불일치), 8080/5432 포트 충돌,  WSL 네트워킹 문제 등을 하나씩 겪으며 원인 진단 → 해결 과정을 반복. 매번 에러 로그 전체를 그대로 붙여넣게 해 정확한 원인을 짚음.

### ⑧ 엔티티 설계 원칙을 먼저 정하고 시작

코드를 바로 요청하지 않고 "Lombok 애노테이션을 어디까지 쓸지, JPA 연관관계를 어떻게 매핑할지" 먼저 물어 원칙(Setter 대신 도메인 메서드, FK 스냅샷 분리, enum STRING 저장, `OffsetDateTime` 사용)을 세운 뒤 Member → ExtensionPolicy → AuditLog 순으로 구현.

### ⑨ `ExtensionNormalizer` + 단위테스트 32건

정규화 로직을 코드로 받은 뒤 바로 신뢰하지 않고 "단위 테스트를 먼저 만들고 검증하자"고 요구 
→ 실행 결과 tab 문자 케이스 하나가 실패. 실패 로그를 그대로 전달해 원인(trim보다 제어문자 검사가 먼저 실행됨)을 찾아 순서 수정 (4-3 "AI가 놓쳤거나 틀렸는데 직접 잡아낸 것" 참고).

### ⑩ 에러 처리 구조 리팩터링 제안

개별 예외 클래스 5개로 만들어둔 걸 보고 "`fileuploadpolicy.global.exception`
패키지를 만들어서 `ErrorCode` enum과 `GlobalExceptionHandler`, `ErrorResponse`
등으로 재사용하게끔 하는 건 어떠냐"고 먼저 구조 개선을 제안
 → 이후 전체 도메인에 이 구조를 일관 적용.

### ⑪ `upload` 도메인 구현 및 실제 파일로 검증

`FileNameParser`(이중 확장자 조각 분리), `MagicByteValidator`(PE/셔뱅 시그니처) 구현 후, 실제로 `malware.exe`(진짜 PE 헤더), `report.jpg`(확장자는 jpg지만 내용은 실행파일)를 만들어 요청해 받은 뒤 Swagger로 직접 업로드 테스트. 이 과정에서 Swagger가 멀티파트 업로드를 문자열 배열로 잘못 인식하는 버그의 원인(`consumes` 속성 누락)을 찾아 수정 (4-3 "AI가 놓쳤거나 틀렸는데 직접 잡아낸 것" 참고).

### ⑫ 더미 로그인 및 감사 로그 검증

"고정확장자 정책은 로그인 여부와 무관하게 전역 상태인 게 맞냐"고 스스로 반문하며 시나리오(test1이 exe/js 차단, test2가 exe만 차단했을 때 서로 다르게 보여야 하는 거 아니냐)를 구체적으로 만들어 재확인 
→ curl로 실제 재현 검증 후 "정책은 전역 상태" 원칙을 명문화 (4-3 "AI 답변을 검증 없이 신뢰하지 않은 것" 참고).

### ⑬ 업로드 이력/다운로드 기능 추가 (요구사항 확장)

로그인 사용자가 과거 업로드 파일을 다시 조회/다운로드할 수 있어야 한다는 요구를 추가하면서, 앞서 CONSIDERATIONS.md에 "한계로만 남겨뒀던" 인증 기반 다운로드 API를 실제로 구현하게 됨. 이 과정에서 "Content-Disposition 헤더 인젝션" 취약점을 스스로 짚어 방어 코드를 제안했고, 필요성을 되물어 확인한 뒤 채택.

### ⑭ 감사 로그 조회 API 누락 발견

프론트 목업 디자인(스크린샷)에 "변경 이력" 테이블이 있는 걸 보고 코드 분석으로 해당 코드가 없음을 확인 → 저장(쓰기) 로직만 있고 조회(GET) API가 빠져있던 걸 발견해 추가(4-3 "AI가 놓쳤거나 틀렸는데 직접 잡아낸 것" 참고).

### ⑮ Docker 통합 및 NCP 배포

`Dockerfile`(백엔드/프론트), `nginx.conf`를 처음부터 하나씩 만들어가며 Windows PowerShell 환경에 맞는 명령어로 안내. NCP 서버 생성 화면 스크린샷을 공유했을 때 "불필요한 RDP(3389) 포트가 열려 있다"는 걸 먼저 짚어 삭제, SSH 접근 제한 필요성도 함께 언급. GitHub push 시 DNS 에러, 서버 SSH 재접속, Git 인증 토큰 발급 등 실제 배포 과정의 자잘한 문제들을 그때그때 캡처해 공유하며 순서대로 해결.

### ⑯ 컨테이너 재시작 정책 추가

배포 완료 후 "서버가 예기치 않게 재부팅되면 컨테이너도 자동으로 다시 떠야 하지 않냐"는 운영 관점 질문으로 `restart: unless-stopped`를 전 서비스에 추가.

### ⑰ 코드 리팩터링 — "주석은 쓰지 말아주세요"

전체 백엔드 코드를 도메인별로 다시 검토받으며 리팩터링 요청. 이 과정에서 호출되지 않는 Repository 메서드(`countByType` 등 죽은 코드 후보)를 발견해 질문, `GlobalExceptionHandler`의 `MaxUploadSizeExceededException` 처리가 `ErrorCode` 없이 하드코딩되어 있던 불일치를 발견해 전용 코드 (`FILE_SIZE_EXCEEDED`)로 통일. (4-3 "AI가 놓쳤거나 틀렸는데 직접 잡아낸 것" 참고).

| Playwright (`run` 스킬) | 로그인 → 업로드 → 이력 확인까지 실제 브라우저 클릭 테스트 | curl로는 못 잡는 렌더링/콘솔 에러 검증 (실제로 게스트 401 콘솔 에러를 이 방식으로 발견) |
| Docker / Docker Compose | 로컬 통합 환경 구성, NCP 배포 | postgres/backend/frontend를 동일한 방식으로 로컬·배포 양쪽에서 실행 |
| Swagger UI | 모든 백엔드 API의 실제 호출 검증 | 코드 리뷰만으로 못 잡는 문제(멀티파트 인식 오류 등)를 실제 호출로 발견 |

# 4-3. 판단 근거 회고

AI가 준 결과를 그대로 쓴 것도 있고, 반박해서 고쳐 쓴 것도 있고, 아예 폐기한 것도 있습니다. 유형별로 실제 있었던 흐름 그대로 정리합니다.

## 고쳐 쓴 것

- **이중 확장자 검사 규칙**.
    - AI가 처음 "마지막 확장자만 검사하면 된다"는 규칙을 제시
    →  "그럼 `.tar.gz`처럼 점이 여러 개인 파일은 다시 작성하라고 해야 하는 거 아니냐"고 반문
    →  점이 2개 이상이면 무조건 문제라고 판단하는 근거가 뭔지 물은 것이었는데, AI가  "마지막 확장자만 보는 방식 자체가 `file.exe.txt` 같은 우회에 뚫린다"는 걸 인정
- **업로드 개수 제한 1개**.
    - AI가 "크기 제한은 걸되 개수는 1개로 하자"고 했을 때 바로 "이 과제 제출 시에도 최소 2개 이상 업로드해서 테스트해야 하는데 1개로 제한하는 건 너무 비현실적이지 않냐"고 반박했다. AI 제안이 스펙 자체는 말이 되는데 실사용 맥락(정상 파일 + 차단 대상 파일을 동시에 검증해야 하는 이 과제 특성)을 놓친 경우라, 근거를 대며 밀어붙여 10개로 바꿨다.
- **`ExtensionNormalizer`의 결과 타입**
    - AI가 준 6단계 결과 객체(enum 실패 사유 포함) 방식 대신 `Optional<String>` 기반으로 직접 단순화하고, RTLO(U+202E) 등 유니코드 포맷 문자 차단을 AI 초안에 없던 항목으로 스스로 추가
- **스키마의 FK 구조**
    - 최초엔 스냅샷 단독이었으나, "테이블끼리 연관관계가 없다"는 지적으로 FK(`ON DELETE SET NULL`)+스냅샷 병행 구조로 보완
- **"게스트도 업로드 이력을 볼 수 있게 해달라"는 요청에 대해, AI(Claude Code)는 1차로 "백엔드의 인증 요구사항을 완화하자"고 제안**
    - 진단(증상: 401)은 정확했지만, 해법은 "이 프로젝트에서 업로드 이력 조회가 왜 로그인을 전제로 설계됐는지"(본인 확인이 안 되면 여러 게스트의 기록이 뒤섞여 노출된다는 문제)를 고려하지 않은 채 나온 것이었음.
    이 시점에 "방금 한 행동의 응답(로그인 불필요)"과 "과거 이력 재조회(로그인 필요)"는 서로 다른 개념인데 하나로 합쳐져 있었다는 지적을 Claude Code에 전달해 방향을 바로잡음.
    ⇒ 결과적으로 **백엔드는 전혀 건드리지 않고, 프론트엔드 상태를 두 개念으로 분리하는 것만으로 요구사항을 만족**
- **README에 시스템 아키텍처 섹션이 빠져있던 것**
    - AI가 처음 준 README에는 아키텍처 다이어그램이 아예 없었다. "이것도 넣어야 하는 거 아니냐"고 지적한 뒤에야 Mermaid 다이어그램이 추가됐다. 처음부터 다이어그램을 그려달라고 알고 요청한 게 아니라, "표준적으로 있어야 할 섹션이 왜 빠졌는지" 문제 제기를 한 것이었다
- **Content-Disposition 헤더 인젝션 방어 코드**
    - 이건 먼저 알아챈 게 아니다. 다운로드 API를 구현하는 과정에서 AI가 "원본 파일명에 개행 문자가 있으면 HTTP 헤더 인젝션이 가능하다"고 먼저 짚어줬다. 다만 그대로 받아쓰지 않고 "이게 진짜 문제가 되는 시나리오인지" 되물어 설명을 들은 뒤에야 반영을 승인했다. AI가
    발견한 걸 베낀 게 아니라, 필요성을 확인하고 채택한 쪽에 가깝다.

## 수용하지 않은 것

- **AI의 최초 기술 스택 추천(Node.js/Next.js)**
    - 실제 경험(Java/Spring)과 채용 공고 요구사항을 근거로 Spring Boot+React로 직접 전환
- **AWS 대신 NCP로 배포 결정**
    - 처음 AI는 채용 공고에 AWS가 명시되어 있다는 이유로 AWS EC2 배포를 추천했다. "실배포 시 AWS는 과금되지 않냐"고 반문했고, "Naver Cloud는 크레딧이 남아있다"는 실질적 이유로 그 제안을 접었다. AI가 다시 정리한 근거(과금 리스크 vs 채용공고 부합도)를 듣고도, "심사 당일 접속이 막히면 안 된다"는 리스크가 더 크다고 판단해 AI의 원래 추천과 반대로 결정했다
- **Kotlin DSL 스캐폴딩**
    - 처음 받은 산출물을 그대로 쓰지 않고 Groovy 기반으로 직접 다시 시작
- **`BaseTimeEntity` 공통 추상화**
    - 중복되는 엔티티가 2개뿐인 시점에 조기 추상화라고 판단해 보류, 각 엔티티에 직접 필드 선언
- **프론트-백엔드 연동 세션(VS Code, Claude Code)에서 나온 백엔드 인증 완화 제안**
    - 게스트도 업로드 이력을 볼 수 있어야 한다는 요구를 처리하면서, Claude Code는 "백엔드의 인증 요구사항 자체를 느슨하게 풀자"고 제안했다. 진단 (증상: 401)은 정확했지만, 해법은 "이 프로젝트에서 업로드 이력 조회가 왜 로그인을 전제로 설계됐는지"(본인 확인이 안 되면 여러 게스트의 기록이 뒤섞여 노출된다는 문제)를 고려하지 않은 채 나온 것이었음. "방금 한 행동의 응답(로그인 불필요)"과 "과거 이력 재조회(로그인 필요)"는 서로 다른 개념인데 하나로 합쳐져 있었다는 지적을, 백엔드 설계를 담당한 다른 세션(claude.ai)의 근거를 그대로 복사해 Claude Code에 반박 자료로 전달했다. 결과적으로 백엔드는 전혀 건드리지 않고, 프론트엔드 상태를 두 개념으로 분리하는 것만으로 요구사항을 만족시켰다 — **여러 AI 도구의 제안이 서로 충돌했을 때, 각 도구가 아니라 설계 근거 자체를 기준으로 판단한 핵심 사례**

## AI의 오류를 찾아서 수정한 것

- **정규화 파이프라인 순서 버그**
    - 코드만 보고 "이상하다" 싶어서 잡아낸 게 아니라, AI가 짜준 `ExtensionNormalizer`를 그대로 믿지 않고 단위테스트를 32개 작성하게 해서 `./gradlew test`를 직접 돌렸다. 실제로 하나가 실패했다 — 탭 문자(`\tsh\t`) 케이스가 통과해야 하는데 빈 값이 나왔다. 실패 로그를 그대로 AI에게 던져줬고, AI가 원인(제어문자 거부를 trim보다 먼저 실행해서 tab이 오분류됨)을 찾아 순서를 고쳤다. "코드가 맞는지는 실행해봐야 안다"는 걸 실제로 겪은 사례로, 코드 리뷰만으로는 못 잡았을 버그.
- **Swagger 멀티파트 인식 오류**
    - 코드는 컴파일도 되고 논리적으로도 문제없어 보였는데, 실제로 Swagger UI를 열어 파일 업로드 API를 눌러보니 `files` 파라미터가 문자열 배열 입력창으로 떠 있었다. 스크린샷을 그대로 공유했고, AI가 `consumes` 속성 누락이 원인이라고 진단해 고쳤다
- **감사 로그 조회(GET) API 누락**
    - 프론트 목업 디자인에 "변경 이력" 화면이 있는 걸 근거로 "이 조회 구현 안 된 거 맞냐"고 확인 → 쓰기 로직만 있고 조회 API가 빠진 걸 발견해 추가
- **`GlobalExceptionHandler`의 하드코딩 불일치**
    - 전체 리팩터링 검토 중 `MaxUploadSizeExceededException` 처리가 다른 예외들과 달리 `ErrorCode` 없이 하드코딩 되어 있던 걸 발견해 `FILE_SIZE_EXCEEDED`로 통일
- **`res.json()`이 빈 바디 200 응답에서 파싱 에러를 던지는 버그**
    - 실제 백엔드가 `PATCH .../fixed/{ext}`, `POST .../logout`에 바디 없이 200을 응답하는데, 기존 클라이언트 코드가 이를 파싱하려다 예외를 던지고 "네트워크 오류"로 잘못 표시하던 걸 발견해 수정. AI가 놓쳤던 게 아니라, 기존(이전 작업 결과물) 코드에 있던 버그를 이번 연동 검증 과정에서 찾아낸 것
- **게스트 상태에서 로그인 전용 API를 호출해 401이 콘솔에 찍히던 버그**
    - 브라우저 클릭 테스트 중에만 드러난 문제. curl 검증만으로는 못 잡았을 사례로, E2E 브라우저 테스트를 병행한 이유가 실제로 증명됨
